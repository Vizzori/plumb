# Security and operational risks of AI code-review agents and harnesses in CI (state as of 23 Nov 2026)

Scope note: focus is on open-source review tools and harnesses (PR-Agent, claude-code-action, claude-code-security-review, run-gemini-cli / Gemini CLI, codex-action / Codex CLI, OpenHands, OpenCode, Kodus, OpenHarness, Cline's workflows). Proprietary incidents are included only where instructive and are labelled **[PROPRIETARY]**. Vendor statements are labelled **[VENDOR STATEMENT]**. Where a fact comes only from secondary coverage or a search-result summary rather than the primary page, it is labelled **(secondary)**.

---

## 1. Prompt injection via untrusted PR content (titles, descriptions, comments, commit messages, hidden Unicode / HTML comments, rules/instruction files)

### Takeaway
Between 2024 and 2026 prompt injection through attacker-controlled PR/issue metadata, comments, commit messages, hidden HTML comments, invisible Unicode and repository instruction files (CLAUDE.md, AGENTS.md, .cursorrules, .gemini/, .mcp.json) was demonstrated against essentially every major AI review/agent harness, with outcomes ranging from manipulated review verdicts to secret theft and supply-chain compromise. The damage is determined by what the agent can do (shell, write tokens, network, secrets in env) far more than by the model: model refusals happened in some attacks but are not reliable, and vendors increasingly state openly that their agents are "not hardened" against injection.

### Cited Findings

**Injection vectors (attacker-controlled fields)**
- Aikido's "PromptPwnd" (published 4 Dec 2025, author Rein Daelman) documents prompts built from `github.event.issue.title`, `github.event.issue.body`, `github.event.pull_request.body` and commit messages; affected harnesses: Gemini CLI via `google-github-actions/run-gemini-cli`, Claude Code Actions, OpenAI Codex Actions, GitHub AI Inference. Aikido notes that passing fields via environment variables prevents shell injection but "do[es] not protect against prompt injection" — [Aikido](https://aikido.dev/blog/promptpwnd-github-actions-ai-agents)
- "Comment and Control" (Aonan Guan with Johns Hopkins researchers Zhengyu Liu and Gavin Zhong; SecurityWeek article 16 Apr 2026, updated 21 Apr 2026): a crafted **PR title** hijacked Anthropic's Claude Code Security Review action; an **issue title plus crafted issue comments** hijacked the Gemini CLI Action; a **hidden HTML comment in an issue body** hijacked GitHub's Copilot coding agent (victim must assign the issue to Copilot) — [SecurityWeek](https://www.securityweek.com/claude-code-gemini-cli-github-copilot-agents-vulnerable-to-prompt-injection-via-comments/); CSA adds that the Gemini attack used a fake "trusted content" marker in a comment and the Copilot payload base64-encoded secrets to evade secret scanning and exfiltrated via `git push` — [CSA, 7 Aug 2026](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-coding-agent-ci-prompt-injection-202608/)
- CamoLeak **[PROPRIETARY: GitHub Copilot Chat]**: instructions hidden in a PR description using GitHub's invisible markdown-comment syntax; invisible in the web UI but read by Copilot Chat, and the injection affected *other users* who opened the PR in Copilot Chat — [Legit Security](https://www.legitsecurity.com/blog/camoleak-critical-github-copilot-vulnerability-leaks-private-source-code)
- Trail of Bits (6 Aug 2025) **[PROPRIETARY: Copilot coding agent]**: hidden instructions inside a GitHub issue made the Copilot agent (once a maintainer assigned the issue) insert a backdoor into an otherwise legitimate PR (demo: "add Spanish/French support" via flask-babel) — [Trail of Bits](https://blog.trailofbits.com/2025/08/06/prompt-injection-engineering-for-attackers-exploiting-github-copilot/)
- OpenAI's codex-action security guide lists as untrusted: PR titles and bodies ("Hidden HTML comments (`<!-- -->`) can carry instructions"), commit messages, repository instruction files from PR content (`AGENTS.md`, `AGENTS.override.md`, fallback project docs), screenshots and other media — [codex-action docs/security.md](https://github.com/openai/codex-action/blob/main/docs/security.md)
- claude-code-action's sanitizer strips HTML comments, invisible characters, markdown image alt text, hidden HTML attributes and HTML entities, but its docs warn "new bypass techniques may emerge" and advise reviewing raw external content — [claude-code-action docs/security.md](https://github.com/anthropics/claude-code-action/blob/main/docs/security.md)
- Hidden Unicode in rules files: Pillar Security's "Rules File Backdoor" (18 Mar 2025) hid instructions in Cursor/Copilot rule files using invisible Unicode (zero-width joiners, bidirectional markers); the demo rule ("follow HTML5 best practices") made the assistant append an external script to generated files without mentioning it, and the characters are not visible in GitHub PR review — [Pillar](https://pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents); [The Hacker News](https://thehackernews.com/2025/03/new-rules-file-backdoor-attack-lets.html)
- GitHub response at platform level: on 1 May 2025 GitHub started showing a warning when a file contains hidden Unicode text "that can be interpreted differently than it appears", explicitly mentioning AI tools — [GitHub changelog](https://github.blog/changelog/2025-05-01-github-now-provides-a-warning-about-hidden-unicode-text); this extends the 31 Oct 2021 bidirectional-text warning introduced for "Trojan Source" (CVE-2021-42574) — [GitHub changelog 2021](https://github.blog/changelog/2021-10-31-warning-about-bidirectional-unicode-text/)
- Repository instruction/config files as injection carriers:
  - hackerbot-claw (Feb–Mar 2026) tried a poisoned `CLAUDE.md` against an AI code reviewer in `ambient-code/platform`; detected, and Claude did not execute the instructions — [StepSecurity](https://www.stepsecurity.io/blog/hackerbot-claw-github-actions-exploitation)
  - Novee Security (Black Hat USA, 5 Aug 2026): in OpenAI's own issue-dedup workflow two Codex passes shared one writable checkout; the first (manipulated) pass wrote an `AGENTS.md` that the second pass loaded as instructions — [Hackread](https://hackread.com/black-hat-usa-2026-github-compromise-ai-coding/)
  - claude-code-action GHSA-8q5r-mmjf-575q: a `.mcp.json` in the PR head was loaded and all project MCP servers enabled → RCE on the runner — [OSV](https://osv.dev/vulnerability/GHSA-8q5r-mmjf-575q)
  - Gemini CLI GHSA-wpqr-6v78-jr5g: headless mode auto-trusted the workspace, so a malicious local `.gemini/` directory (environment variables) could lead to RCE — [OSV](https://osv.dev/vulnerability/GHSA-wpqr-6v78-jr5g)
  - OpenHarness (HKUDS) CVE-2026-56696 (23 Jun 2026): remotely invocable `/issue` and `/pr_comments` slash commands wrote attacker Markdown into `.openharness/issue.md` / `pr_comments.md`, which are injected into the runtime system prompt — a *persistent* injection — [VulnCheck](https://www.vulncheck.com/advisories/openharness-prompt-injection-via-issue-and-pr-comments-slash-commands)
- Comment-command injection in a review bot: in PR-Agent the text after `/ask` went straight into the LLM prompt, letting anyone make the bot post attacker-controlled comments under its own token; on GitLab those comments could trigger quick actions (`/approve`, `/rebase`, `/assign`, `/title`, `/close`, `/lock`, `/target_branch`) with the bot's privileges — [Kudelski Security, 29 Aug 2024](https://kudelskisecurity.com/research/careful-where-you-code-multiple-vulnerabilities-in-ai-powered-pr-agent)

**What attackers achieved**
- Secret exfiltration into public issues/comments/logs: in PromptPwnd the PoC issue told the agent to write secrets into the issue body with `gh issue edit`; Google's own `gemini-cli` repo workflow exposed `GEMINI_API_KEY`, `GOOGLE_CLOUD_ACCESS_TOKEN` and a read/write `GITHUB_TOKEN` — [Aikido](https://aikido.dev/blog/promptpwnd-github-actions-ai-agents); in Comment and Control a PR title made Claude run `ps auxeww`, exposing `ANTHROPIC_API_KEY` and `GITHUB_TOKEN` in a public PR comment — [CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-coding-agent-ci-prompt-injection-202608/)
- Code execution / supply-chain compromise: Clinejection — an issue title made Claude run `npm install` on an attacker commit (preinstall script), then pivot via cache poisoning to release tokens — [Adnan Khan](https://adnanthekhan.com/posts/clinejection/); Flatt Security — an issue made Claude read `/proc/self/environ` and write OIDC request credentials into the issue, which could be exchanged for a write token to `anthropics/claude-code-action` itself — [GMO Flatt Security](https://flatt.tech/research/posts/poisoning-claude-code-one-github-issue-to-break-the-supply-chain/)
- Private-data exfiltration: Invariant Labs (26 May 2025) — a malicious issue in a public repo coerced an agent using the GitHub MCP server to pull private-repo data into a public PR ("toxic agent flow"); Invariant called it architectural, not a server bug — [Invariant Labs](https://invariantlabs.ai/blog/mcp-github-vulnerability); CamoLeak leaked private code, AWS keys and undisclosed vulnerability descriptions one character at a time via GitHub's Camo image proxy — [Legit Security](https://www.legitsecurity.com/blog/camoleak-critical-github-copilot-vulnerability-leaks-private-source-code)
- Review-verdict manipulation (most directly relevant to review bots): "When AI Agrees Too Much: Manipulating Automated Code Review via Bias Injection" (Alexopoulos, Alexopoulos, Spinellis, Mitropoulos; v1 19 Mar 2026, v5 27 Oct 2026, slated for ICSE 2027) crafted PR metadata to bias Claude Code and CodeRabbit review pipelines into missing reintroduced vulnerabilities; template-based attacks were ineffective and "may even backfire", but LLM-assisted iterative refinement succeeded in 32 of 33 cases (97%) across 33 CVEs in 20 projects; attackers can iterate against a local clone while defenders get one shot — [arXiv 2603.18740](https://arxiv.org/abs/2603.18740)
- Counter-evidence: "Can Adversarial Code Comments Fool AI Security Reviewers" / "LLM Code Reviewers Are Harder to Fool Than You Think" (Feb 2026) tested 8 comment strategies × 8 models × 100 vulnerable samples and concluded adversarial *code comments* are not the main threat — inherent detection difficulty is; one defence even degraded detection for weaker models — [arXiv 2602.16741](https://arxiv.org/abs/2602.16741) (secondary summary of findings)

**Model resistance is real but unreliable**
- Datadog (9 Mar 2026): the `claude-code-action` triage workflow in `datadog-agent` "identified and ignored" hackerbot-claw's injection attempts (bulk-label issues, edit CODEOWNERS, override instructions) — [Datadog](https://www.datadoghq.com/blog/engineering/stopping-hackerbot-claw-with-bewaire)
- Wiz (30 Apr 2026): Gemini refused to create an issue containing GCP service-account credentials but still printed them into the workflow log; verbose modes leaked secrets "even though the model recognized them as sensitive"; Wiz's working assumption is that if an attacker controls input, injection will succeed — [Wiz](https://wiz.io/blog/github-actions-security-ai-powered-actions-vulnerabilities)
- **[VENDOR STATEMENT – Anthropic]** The `claude-code-security-review` README: "This action is not hardened against prompt injection attacks and should only be used to review trusted PRs" — [GitHub repo](https://github.com/anthropics/claude-code-security-review)
- **[VENDOR STATEMENT – GitHub]** GitHub classified the Comment and Control Copilot-agent finding as a "known architectural limitation", not a vulnerability; researcher Guan: "the prompt injection here is not a bug; it is context that the agent is designed to process" — [SecurityWeek](https://www.securityweek.com/claude-code-gemini-cli-github-copilot-agents-vulnerable-to-prompt-injection-via-comments/)

### Inferences
- For review-only bots (no shell, comment-only token) the realistic worst case is verdict manipulation (missed vulnerabilities, false "LGTM") and comment abuse; for agentic harnesses with shell/MCP/write tokens the worst case becomes RCE, secret theft and supply-chain compromise. Hardening should therefore start by shrinking capabilities, not by prompt engineering.
- Hidden-content tricks (HTML comments, invisible Unicode) specifically defeat *human* oversight: the maintainer reviewing the PR or issue literally cannot see what the bot read. Sanitizers like claude-code-action's help, but visible injections in titles/bodies remain.
- Instruction/config files supplied by the PR (CLAUDE.md, AGENTS.md, .cursorrules, .gemini/, .mcp.json, .pr_agent.toml) must be treated as executable code: load them from the base branch, protect with CODEOWNERS, or ignore them for untrusted PRs.
- The 97% bias-injection result suggests an AI reviewer should never be the sole gate for merging external contributions, especially when attackers can rehearse against the same open-source pipeline.

### Gaps
- No public, systematic measurement of injection success against specific OSS review bots such as PR-Agent or Kodus was found.
- Whether GitHub fixed the underlying injection in CamoLeak (vs. only closing the image-rendering channel) is not stated in the Legit write-up.
- GitHub's response to the Trail of Bits Copilot-agent backdoor demo was not found.
- Exact defence results of arXiv 2603.18740 are not in the abstract; full paper not reviewed.

## 2. Specific incidents and advisories (dated, with root cause and fix status)

### Takeaway
The record from mid-2024 to Nov 2026 shows a consistent pattern: every major harness (PR-Agent, claude-code-action and Claude Code, run-gemini-cli/Gemini CLI, Codex/codex-action, OpenHands, OpenCode) has had at least one advisory or published exploit chain, usually combining untrusted input + over-privileged token/secrets + an exfiltration or execution channel; fixes are often point fixes (block `ps`, add guardrail prompts, blocklists) that researchers then bypass, and real-world exploitation has already happened (Nx s1ngularity, Cline, hackerbot-claw, Trivy).

### Cited Findings

#### 2.1 Chronology of key incidents/research

**PR-Agent / Qodo Merge (OSS PR-Agent; hosted Qodo Merge Pro is proprietary)**
- 29 Aug 2024 (updated 1 Oct and 8 Nov 2024), Kudelski Security (Nils Amiet), "Careful Where You Code": `/ask` prompt injection → bot posts attacker content; GitLab quick-action privilege escalation; config overwrite through `--some.key=value` command arguments (found via `/update_changelog`); overriding `gitlab.url`, `github.base_url` or `openai.api_base` leaked GitLab token, `GITHUB_TOKEN`, GitHub App JWT and OpenAI/Azure keys; with the docs-recommended `contents: write`, a leaked token could modify repos/releases. Tested on v0.23. CVE-2024-51355 and CVE-2024-51356 assigned. Timeline: reported 18 Jul 2024, no substantive vendor response; publication 29 Aug 2024; on 8 Nov 2024 "The PoC described above works again on the latest git version of Qodo Merge" — i.e. **not fixed** at that time — [Kudelski](https://kudelskisecurity.com/research/careful-where-you-code-multiple-vulnerabilities-in-ai-powered-pr-agent). Presented at 38C3 (Dec 2024) as "AI Meets Git: Unmasking Security Flaws in Qodo Merge", including difficulty contacting the vendor — [38C3 Fahrplan](https://fahrplan.events.ccc.de/congress/2024/fahrplan/talk/XXXSWE/) (secondary)
- 15 Jan 2026, Kudelski follow-up "Qodo/Dynaconf: AWS admin key leaked twice": Qodo's argument blocklists were bypassed with Dynaconf dynamic variables (`@json`, `@jinja`, Jinja `__setattr__`); a repo `.pr_agent.toml` using `@format` exposed env vars of Qodo Merge Pro, including an AWS key with AdministratorAccess; later RCE on the production GitHub-app server via `dynaconf_include` + a race in `/help_docs`. Timeline: 12 Mar 2025 first bypass; 7 Apr 2025 AWS key leak; 8 Apr 2025 fix deployed; **17 May 2025 PR-Agent v0.29 released with the fix for OSS users**; 30 Sep 2025 RCE disclosed; 22 Oct 2025 full fix confirmed; 24 Oct 2025 AWS key rotation confirmed. Final fix: `AUTO_CAST_FOR_DYNACONF=false` and an in-house loader blocking includes. Kudelski: all described issues fixed as of Oct 2025 — [Kudelski](https://kudelskisecurity.com/research/qodo-dynaconf-aws-admin-key-leaked-twice)
- **[VENDOR STATEMENT – Qodo, 30 Dec 2025]** Remediated an RCE "under specific conditions" in Qodo and in PR-Agent; no indication of in-the-wild exploitation or customer-data access; plans to hire AppSec staff and engage external experts — [Qodo blog](https://www.qodo.ai/blog/security-at-qodo-in-2026-our-commitment-recent-learnings-and-whats-next)
- Current state (Nov 2026): the community repo states `/help_docs` "has been disabled since v0.36.1 while a fix is pending for a credential-exposure issue (#2445)" — [The-PR-Agent/pr-agent](https://github.com/The-PR-Agent/pr-agent); [qodo-ai/pr-agent](https://github.com/qodo-ai/pr-agent)

**CodeRabbit [PROPRIETARY, instructive for running linters on untrusted code]**
- Published 19 Aug 2025 (Black Hat USA 2025), Kudelski (Nils Amiet): CodeRabbit ran RuboCop on PR code; a PR-supplied `.rubocop.yml` with `require: ./ext.rb` made RuboCop execute attacker Ruby, which exfiltrated env vars. RuboCop was *outside* CodeRabbit's isolation mechanism. Exposed: Anthropic/OpenAI and other API keys, the CodeRabbit GitHub App private key/client secret, webhook secrets, PostgreSQL credentials, encryption password/salt, etc. Impact claim: app installed 80,000+ times; ~1M repositories; installation tokens could read private repos and rewrite history/releases. Timeline: reported 24 Jan 2025, acknowledged same day; fix confirmed 30 Jan 2025. CodeRabbit disabled RuboCop, rotated credentials within hours, moved RuboCop into the sandbox, audited other services, automated sandbox enforcement. Lesson: "Assume that the user may be able to run untrusted code through these tools"; run tools isolated, pass no env vars, restrict egress — [Kudelski](https://kudelskisecurity.com/research/how-we-exploited-coderabbit-from-a-simple-pr-to-rce-and-write-access-on-1m-repositories)

**Pillar "Rules File Backdoor" [PROPRIETARY tools: Cursor, GitHub Copilot]**
- 18 Mar 2025; disclosed to Cursor Feb 2025 and GitHub Mar 2025; **[VENDOR STATEMENTS]** Cursor said it was not a platform vulnerability and that managing the risk is the user's responsibility; GitHub likewise put review responsibility on developers — [Pillar](https://pillar.security/blog/new-vulnerability-in-github-copilot-and-cursor-how-hackers-can-weaponize-code-agents); [The Hacker News](https://thehackernews.com/2025/03/new-rules-file-backdoor-attack-lets.html). Disclosed to All-Hands AI on 13 Mar 2025; acknowledged 30 Mar 2025; published 140+ days later; **no fix stated** — [Embrace The Red](https://embracethered.com/blog/posts/2025/openhands-remote-code-execution-zombai)

**Gemini CLI (OSS) – Tracebit**
- Reported to Google VDP 27 Jun 2025; Tracebit post 28 Jul 2025: in default config Gemini CLI could silently run arbitrary code when used on untrusted code. Chain: prompt injection hidden in a README (inside GPL licence text) + flawed allowlist matching (a benign `grep` got allow-listed, then `; malicious command` appended on the same line) + misleading UX; could exfiltrate credentials via `env`/`curl`. Fixed in **v0.1.14** (malicious commands now shown; additional binaries need explicit approval). Tracebit also noted "no sandbox" is Gemini CLI's default — [Tracebit](https://tracebit.com/blog/code-exec-deception-gemini-ai-cli-hijack); [CyberScoop](https://cyberscoop.com/google-gemini-cli-prompt-injection-arbitrary-code-execution/) (secondary)

**Amazon Q Developer VS Code extension (open-source repo; product is AWS's)**
- AWS bulletin AWS-2025-015, published 23 Jul 2025, updated 25 Jul 2025; CVE-2025-8217 / GHSA-7g7f-ff96-5gcw. Malicious code was committed to the extension's open-source repo and automatically shipped in **v1.84.0**; it was intended to make changes to services/customer environments but **did not execute because of a syntax error**. Root cause: "a GitHub token with excessive scope in the CodeBuild configuration". Remediation: credentials revoked, v1.84.0 pulled, **v1.85.0** released — [AWS](https://aws.amazon.com/security/security-bulletins/AWS-2025-015/); [NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-8217). Note: SentinelOne's DB calls it RCE, which conflicts with AWS/NVD ("inert") — (secondary)

**Nx "s1ngularity" (weaponised local AI CLIs)**
- Root cause per Nx GHSA-cxm3-wv7p-598c: a workflow merged 21 Aug 2025 used `pull_request_target` and interpolated `${{ github.event.pull_request.title }}` into a `run:` block (bash injection); it was reverted 22 Aug but still triggerable from outdated branches; the attacker used it to trigger `publish.yml` and exfiltrate the npm token. Malicious versions published 26 Aug 2025 from 18:32 EDT, removed 22:44 EDT; advisory 27 Aug 2025. Payload (postinstall) inventoried secrets/wallets, exfiltrated to `s1ngularity-repository` repos under the victim's account, and appended `sudo shutdown -h 0` to shell rc files. Remediation: npm Trusted Publishing, 2FA, token rotation, approval for external-contributor workflows, `SECURITY.md` — [Nx advisory](https://github.com/nrwl/nx/security/advisories/GHSA-cxm3-wv7p-598c)
- AI angle: the payload invoked locally installed AI CLIs with permission-bypass flags — `claude --dangerously-skip-permissions -p`, `gemini --yolo -p`, and Amazon Q with `--trust-all-tools` — to search the filesystem — [Snyk](https://snyk.io/blog/weaponizing-ai-coding-agents-for-malware-in-the-nx-malicious-package)

## 3. CI configuration pitfalls

### Takeaway
Nearly every incident above was enabled by a small set of well-known GitHub Actions anti-patterns — `pull_request_target` with untrusted checkout, write-scoped or long-lived tokens, secrets present in the agent's environment, comment/issue triggers open to anyone, relaxed actor allowlists (`*`, bots), shared caches, verbose logs, and agents with unrestricted shell — and AI agents add a new twist: even when expressions are passed safely via env vars, the *model* still reads attacker text. GitHub is tightening platform defaults (default-branch `pull_request_target` since 8 Dec 2025; `actions/checkout` v7 refusing pwn-request checkouts since 18 Jun 2026; `pull_request_target` blocked by default in public repos from 2 Dec 2026).

### Cited Findings

**`pull_request_target` + untrusted checkout ("pwn request")**
- `pull_request_target` runs in the base repo context with read/write `GITHUB_TOKEN` and secrets even for fork PRs; GitHub recommends `pull_request` when secrets are not needed — [GitHub Docs](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)
- Real exploitation: Nx (PR-title bash injection in a `pull_request_target` workflow → npm token, Aug 2025) — [Nx advisory](https://github.com/nrwl/nx/security/advisories/GHSA-cxm3-wv7p-598c); awesome-go and Trivy (Feb 2026) — [StepSecurity](https://www.stepsecurity.io/blog/hackerbot-claw-github-actions-exploitation); SpotBugs (Nov 2024) `pull_request_target` PAT theft that led to the reviewdog and tj-actions compromises (CVE-2025-30154, CVE-2025-30066, Mar 2025; ~23,000 repos affected by tj-actions) — [CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-github-actions-security-20260503-csa-st/)
- claude-code-action guidance: for `pull_request_target`/`workflow_run`, do not check out an untrusted ref into the workspace root; check out base and put PR head in a subdirectory passed with `--add-dir`; the action restores `.claude/`, `.mcp.json`, `CLAUDE.md`, `.husky/` etc. from the base branch on PRs — [claude-code-action security.md](https://github.com/anthropics/claude-code-action/blob/main/docs/security.md)
- GitHub platform changes:
  - 7 Nov 2025 changelog, effective 8 Dec 2025: `pull_request_target` always uses the workflow file and checkout commit from the **default branch** (outdated vulnerable workflows on other branches were being exploited — exactly the Nx pattern) — [GitHub changelog](https://github.blog/changelog/2025-11-07-actions-pull_request_target-and-environment-branch-protections-changes/)
  - 18 Jun 2026: `actions/checkout` **v7** refuses to fetch fork PR code in `pull_request_target` and `workflow_run` (from `pull_request*`) workflows (e.g. `ref: ${{ github.event.pull_request.head.sha }}` fails); backported to supported majors from 20 Jul 2026 for floating tags; opt-out `allow-unsafe-pr-checkout`; does **not** cover `git`/`gh` fetches in `run:` steps, `issue_comment` events or unrelated repos — [GitHub changelog](https://github.blog/changelog/2026-06-18-safer-pull_request_target-defaults-for-github-actions-checkout)
  - 2 Nov 2026 changelog: from **2 Dec 2026** `pull_request_target` is **blocked by default in public repositories** (Free/Team/Enterprise Cloud, not GHES) unless allowed via an Actions event policy; brownouts on 9 and 16 Nov 2026 (16:00–18:00 UTC) produced failed runs — [GitHub changelog](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2)

**Secrets and fork PRs**
- Under `pull_request` from forks, `GITHUB_TOKEN` is read-only and other secrets are not provided — [GitHub Docs](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target); Anthropic's docs note that on public repos "GitHub withholds secrets from runs triggered by fork pull requests, so the review runs only on pull requests from branches in the same repository" — [Claude Code GitHub Actions docs](https://code.claude.com/docs/en/github-actions)
- Anthropic recommends enabling "Require approval for all external contributors" for its security-review action — [claude-code-security-review](https://github.com/anthropics/claude-code-security-review)

**Over-privileged / long-lived tokens**
- PR-Agent docs recommended `contents: write`, which turned a leaked `GITHUB_TOKEN` into repo/release write access — [Kudelski 2024](https://kudelskisecurity.com/research/careful-where-you-code-multiple-vulnerabilities-in-ai-powered-pr-agent)
- Amazon Q: "a GitHub token with excessive scope in the CodeBuild configuration" — [AWS](https://aws.amazon.com/security/security-bulletins/AWS-2025-015/)
- Qodo Merge Pro: AWS key with AdministratorAccess reachable from the app's environment, unchanged after the first disclosure — [Kudelski 2026](https://kudelskisecurity.com/research/qodo-dynaconf-aws-admin-key-leaked-twice)
- `id-token: write` turns any agent compromise into OIDC-token theft (Flatt chain) — [Flatt](https://flatt.tech/research/posts/poisoning-claude-code-one-github-issue-to-break-the-supply-chain/); note the default `@claude` workflow in Anthropic's docs grants `contents: write`, `pull-requests: write`, `issues: write`, `id-token: write` — [Claude docs](https://code.claude.com/docs/en/github-actions)
- The official Claude GitHub App requests a broad permission set (incl. Actions, Workflows, Repository hooks and Repository creation read/write) that cannot be partially accepted; Anthropic suggests a custom App with only Contents, Issues, Pull requests if that matters — [Claude docs](https://code.claude.com/docs/en/github-actions)

**Comment/issue-triggered workflows invoked by untrusted users**
- hackerbot-claw used `/version minor`, `/format`, `/sync-metadata` comment triggers to reach script/branch-name/filename injection — [StepSecurity](https://www.stepsecurity.io/blog/hackerbot-claw-github-actions-exploitation)
- AI issue-triage workflows (Gemini CLI repo; Cline; Anthropic's own `claude-code` repo) were triggerable by anyone who opens an issue — [Aikido](https://aikido.dev/blog/promptpwnd-github-actions-ai-agents); [Adnan Khan](https://adnanthekhan.com/posts/clinejection/); [Flatt](https://flatt.tech/research/posts/poisoning-claude-code-one-github-issue-to-break-the-supply-chain/)
- Relaxed allowlists: `allowed_non_write_users: "*"` ("extremely dangerous" per Aikido), codex `allow-users: "*"` (API-key abuse), `allowed_bots: "*"` / `allow-bots: true` (attacker Apps), Dependabot as confused deputy — [Aikido](https://aikido.dev/blog/promptpwnd-github-actions-ai-agents); [codex-action security.md](https://github.com/openai/codex-action/blob/main/docs/security.md); [Wiz](https://wiz.io/blog/github-actions-security-ai-powered-actions-vulnerabilities)
- Actions without built-in access control (PR-Agent action, coderabbitai/ai-pr-reviewer, claude-code-security-review) need `author_association` checks (OWNER/MEMBER/COLLABORATOR) on comment triggers — [Wiz](https://wiz.io/blog/github-actions-security-ai-powered-actions-vulnerabilities)

**Agents with shell access / weak tool allowlists**
- Cline gave the triage agent `Bash`, `Write`, `Edit` → arbitrary code in a default-branch workflow — [Adnan Khan](https://adnanthekhan.com/posts/clinejection/)
- Allowlist-matching flaws: Gemini CLI `grep` prefix + `;` (Jul 2025) — [Tracebit](https://tracebit.com/blog/code-exec-deception-gemini-ai-cli-hijack); allowlists ignored under `--yolo` (2026) — [OSV](https://osv.dev/vulnerability/GHSA-wpqr-6v78-jr5g); Claude Code validator bypassed via `git push --receive-pack` — [Hackread](https://hackread.com/black-hat-usa-2026-github-compromise-ai-coding/); `cat` of `/proc/self/environ` permitted without approval — [Flatt](https://flatt.tech/research/posts/poisoning-claude-code-one-github-issue-to-break-the-supply-chain/)
- With passwordless sudo (default on GitHub-hosted runners) a read-only filesystem policy is not enough — the API key can be read through procfs — [codex-action security.md](https://github.com/openai/codex-action/blob/main/docs/security.md)

**Other pitfalls**
- Shared Actions cache between low-privilege and release workflows (cache poisoning) — [Adnan Khan](https://adnanthekhan.com/posts/clinejection/)
- Verbose/debug output in public logs (`show_full_output`, auto-enabled when `ACTIONS_STEP_DEBUG=true`; `gemini_debug`) — [claude-code-action security.md](https://github.com/anthropics/claude-code-action/blob/main/docs/security.md); [Wiz](https://wiz.io/blog/github-actions-security-ai-powered-actions-vulnerabilities)
- Credential files from auth actions sitting in the workspace — [Wiz](https://wiz.io/blog/github-actions-security-ai-powered-actions-vulnerabilities)
- Multi-pass agents sharing a writable workspace (AGENTS.md persistence) — [Hackread](https://hackread.com/black-hat-usa-2026-github-compromise-ai-coding/)
- Expression injection `${{ }}` into `run:` (Nx; hackerbot-claw) — pass via `env:` and quote — [codex-action security.md](https://github.com/openai/codex-action/blob/main/docs/security.md); [StepSecurity](https://www.stepsecurity.io/blog/hackerbot-claw-github-actions-exploitation)
- Unpinned versions: run-gemini-cli defaults `gemini_cli_version` to `latest` (README recommends pinning) — [run-gemini-cli](https://github.com/google-github-actions/run-gemini-cli); conversely floating `@v1` tags received the claude-code-action MCP fix automatically — [OSV](https://osv.dev/vulnerability/GHSA-8q5r-mmjf-575q)
- Scale: GhostAction (Sep 2025) compromised 327 GitHub accounts and stole secrets from 817 repos — [CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-github-actions-security-20260503-csa-st/); hackerbot-claw reportedly scanned ~47,391 repos for misconfigurations — StepSecurity via search coverage (secondary)

### Inferences
- For AI review specifically, the classic choice "review fork PRs with secrets via `pull_request_target`" is now being closed by GitHub (Dec 2026 default block). Teams wanting AI review of external contributions must either use a hosted GitHub App (secrets stay server-side), a two-stage `pull_request` → `workflow_run` design that never executes PR code with secrets, or maintainer-gated triggers.
- Passing untrusted fields via `env:` fixes shell injection but not prompt injection — AI workflows need *both* expression hygiene and capability minimisation.
- The safest review-bot configuration is: `pull_request` trigger, `contents: read` + `pull-requests: write` only, no `id-token: write`, no cloud credentials in the job, no shell/write tools, author_association or write-access gate on comment triggers, and the agent step last in the job.

### Gaps
- Defaults of GitHub's "approval for first-time contributors" setting in 2026 not verified.
- No quantitative census of how many public repos run AI review bots under `pull_request_target` (Wiz gives only workflow counts and star totals).

## 4. Mitigations and how well each OSS harness supports them (plus vendor security guidance)

### Takeaway
The major vendor harnesses now ship meaningful guardrails — write-access gates by default, bot blocking, input sanitisation, process-privilege dropping, sandbox/permission profiles, explicit workspace trust, OIDC/WIF auth — but each vendor explicitly says these are not a security boundary against prompt injection; community review bots (PR-Agent, Kodus, OpenCode, OpenHands resolver) offer far fewer built-in CI controls, so protection must come from the workflow design (least privilege, isolation, egress control, human gates). GitHub's Agentic Workflows "safe outputs" pattern (agent read-only; writes executed by separate, permission-controlled jobs) is the clearest architectural mitigation published so far.

### Cited Findings

**anthropics/claude-code-action (licence not verified in this pass)**

**anthropics/claude-code-security-review (MIT)**
- **[VENDOR STATEMENT]** not hardened against prompt injection; review trusted PRs only; enable "Require approval for all external contributors"; minimal permissions (`pull-requests: write`, `contents: read`); default timeout 20 min — [repo](https://github.com/anthropics/claude-code-security-review)

**google-github-actions/run-gemini-cli + Gemini CLI (Apache-2.0)**
- Auth: Workload Identity Federation recommended as "most secure"; custom GitHub App recommended over default token; best-practices doc: protect branches/tags, restrict PR approvers, pin action versions, review logs; telemetry to own GCP project — [README](https://github.com/google-github-actions/run-gemini-cli)
- Since the Apr 2026 fix: workspace trust must be explicit in headless mode (`GEMINI_TRUST_WORKSPACE`, only for trusted inputs; otherwise follow the repo's hardening guidance); tool allowlists enforced even under `--yolo` — [OSV](https://osv.dev/vulnerability/GHSA-wpqr-6v78-jr5g)
- Weak points: sandbox not the default (per Tracebit, 2025) — [Tracebit](https://tracebit.com/blog/code-exec-deception-gemini-ai-cli-hijack); README does not discuss `pull_request_target`, author_association checks, untrusted input, or `permissions:` — [README](https://github.com/google-github-actions/run-gemini-cli); Wiz rates its tool exposure broad (file write, git push, PR creation, fork) — [Wiz](https://wiz.io/blog/github-actions-security-ai-powered-actions-vulnerabilities); Google's response to Comment and Control was guardrail prompts — [SecurityWeek](https://www.securityweek.com/claude-code-gemini-cli-github-copilot-agents-vulnerable-to-prompt-injection-via-comments/)

**openai/codex-action + Codex CLI**
- Write-access gate by default; `allow-users`, `allow-bots`, `allow-bot-users` (no `*`); `safety-strategy` `drop-sudo` or `unprivileged-user` to keep `OPENAI_API_KEY` secret (procfs risk); `permission-profile` (prefer built-in `:workspace`) for filesystem/network policy; run the action as the last step of the job; treat PR text, commit messages, AGENTS.md as untrusted; don't point `codex-home` at untrusted config — [codex-action security.md](https://github.com/openai/codex-action/blob/main/docs/security.md)
- Codex sandbox modes: `read-only`, `workspace-write` (default locally; network off unless `sandbox_workspace_write.network_access = true`), `danger-full-access`; approval policies (`on-request`, `never`, `auto_review`) — [OpenAI Codex docs](https://developers.openai.com/codex/concepts/sandboxing)
- Wiz: codex-action is sandboxed with limited git push (narrowest blast radius of the reviewed actions) — [Wiz](https://wiz.io/blog/github-actions-security-ai-powered-actions-vulnerabilities)
- **[VENDOR]** after Novee: split agent passes into separate jobs/read-only envs in OpenAI's own repo; other repos must do the same themselves — [Hackread](https://hackread.com/black-hat-usa-2026-github-compromise-ai-coding/)

**PR-Agent (community-maintained since Apr 2026)**
- Does not run repository code in the way CodeRabbit ran linters, but historically exposed config-injection surfaces (command-argument overrides, `.pr_agent.toml`, Dynaconf features) — now constrained by v0.29+ loader changes and the disabled `/help_docs` — [Kudelski 2026](https://kudelskisecurity.com/research/qodo-dynaconf-aws-admin-key-leaked-twice); [The-PR-Agent/pr-agent](https://github.com/The-PR-Agent/pr-agent)
- No built-in actor access control in its GitHub Action per Wiz — add `author_association` checks — [Wiz](https://wiz.io/blog/github-actions-security-ai-powered-actions-vulnerabilities)
- Kudelski's recommendations: guardrail tooling (e.g. NeMo-Guardrails, "likely not 100% bulletproof"), denylist of non-overridable config keys, don't grant `contents: write` — [Kudelski 2024](https://kudelskisecurity.com/research/careful-where-you-code-multiple-vulnerabilities-in-ai-powered-pr-agent)
- Strength: model-agnostic via LiteLLM (Azure OpenAI, Bedrock, Vertex, Ollama, etc.), enabling self-hosted or in-tenant inference — [qodo-ai/pr-agent](https://github.com/qodo-ai/pr-agent)

- SDK offers a confirmation policy (when to ask the user) and a security analyzer (LLM-based risk rating) — both must be configured; analyzer alone does not change confirmation behaviour — [OpenHands SDK security guide](https://docs.openhands.dev/sdk/guides/security) (secondary summary)
- Enterprise GitHub resolver: users must link a GitHub identity to an OpenHands account before `@openhands` triggers jobs; App must be installed — [OpenHands enterprise docs](https://docs.openhands.dev/enterprise/integrations/github.md) (secondary summary)
- Rehberger's advice: run in a sandbox, restrict outbound network to trusted domains, limit data/secrets, require approval for terminal/browsing, treat agents as potential malicious insiders — [Embrace The Red](https://embracethered.com/blog/posts/2025/openhands-remote-code-execution-zombai)

**GitHub Agentic Workflows (gh-aw; research preview) — architectural reference**
- "Safe outputs": the agent runs without write access and emits structured requests; separate permission-controlled jobs perform writes after threat detection and output sanitisation (e.g. secret removal); network firewall; sandboxed agent/MCP processes; unspecified permissions default to none — [GitHub blog, 9 Mar 2026](https://github.blog/2026/03/09/under-the-hood-security-architecture-of-github-agentic-workflows/); [gh-aw safe outputs](https://github.github.com/gh-aw/reference/safe-outputs/) (secondary summary; preview status)

**Cross-cutting mitigations recommended by researchers**
- Kudelski (CodeRabbit): isolate every tool that touches untrusted code, pass no env vars, restrict egress to allowlisted hosts or disable network — [Kudelski](https://kudelskisecurity.com/research/how-we-exploited-coderabbit-from-a-simple-pr-to-rce-and-write-access-on-1m-repositories)
- Aikido: restrict toolsets (especially issue/PR write), avoid untrusted input in prompts, treat AI output as untrusted, limit token blast radius (e.g. IP restrictions), scan workflows (open-sourced Opengrep rules) — [Aikido](https://aikido.dev/blog/promptpwnd-github-actions-ai-agents)
- Wiz: don't rely on model guardrails; avoid relaxed bot settings; add author_association checks; don't combine AI actions with credential-generating auth actions in one workflow; avoid verbosity in public repos — [Wiz](https://wiz.io/blog/github-actions-security-ai-powered-actions-vulnerabilities)
- StepSecurity: egress allowlisting on runners (Harden-Runner), avoid `pull_request_target` + untrusted checkout, gate comment triggers, `contents: read` default, put `CLAUDE.md` under CODEOWNERS, avoid `allowed_non_write_users: '*'` — [StepSecurity](https://www.stepsecurity.io/blog/hackerbot-claw-github-actions-exploitation)
- CSA (Aug 2026): treat every env var available to an agent as exposed; short-lived per-run credentials; egress allowlisting; verify validators check the normalised command the shell executes; separate read-of-untrusted-content from write/credential access; human-in-the-loop so a successful injection yields at most a proposal — [CSA](https://labs.cloudsecurityalliance.org/research/csa-research-note-ai-coding-agent-ci-prompt-injection-202608/)
- Defence in depth that worked in practice: Datadog's org rulesets (no direct default-branch/tag writes) and org setting forbidding Actions from creating/approving PRs contained a successful runner compromise; LLM-based malicious-PR detection (BewAIre) as an additional signal — [Datadog](https://www.datadoghq.com/blog/engineering/stopping-hackerbot-claw-with-bewaire)

### Inferences
- Support matrix (qualitative): claude-code-action and codex-action provide the richest built-in controls (actor gating, sanitisation or privilege dropping, tool/permission profiles); run-gemini-cli relies more on Gemini CLI settings and has had the most severe advisory (CVSS 10); PR-Agent, Kodus, OpenCode and the OpenHands resolver leave actor gating, token scoping and isolation largely to the operator.
- "Read-only token + no secrets except the LLM key + no shell + comment-only output" is achievable with all of them and removes most of the RCE/exfiltration classes; what remains is LLM-key abuse (cost) and verdict manipulation.
- Vendor guardrail-prompt fixes (Google) and command blocklists (Anthropic `ps`) should be treated as weak mitigations; capability removal and job separation are strong ones.

### Gaps
- Licences of claude-code-action, codex-action, OpenHands and OpenCode were not re-verified in this pass.
- Whether the OpenHands GitHub resolver runs with confirmation mode or a security analyzer by default is not documented in the sources found.
- No independent evaluation comparing the effectiveness of claude-code-action's sanitizer vs. other harnesses was found.
- run-gemini-cli's `docs/best-practices.md` and hardening guide were not read in full.

## 5. Data and operational risks (third-party APIs vs self-hosting, retention, licences, cost, reliability)

### Takeaway
Hosted-LLM review means sending diffs (and often surrounding code) to Anthropic/OpenAI/Google, whose default API terms retain inputs/outputs for up to ~30 days for abuse monitoring (longer if flagged) without training on paid/API data; zero-data-retention and in-tenant routing (Bedrock/Vertex/Foundry/Azure) are available but must be arranged. Self-hosting with local models keeps code in-house but, per PR-Agent's own docs, local open models are suitable for experimentation rather than production review. Operationally, the main risks are uncontrolled API spend (open triggers, loops, retries), CI breakage from security-driven behaviour changes, and licence obligations (PR-Agent's AGPL period; Kodus AGPL core).

### Cited Findings

**Data sent to third-party LLM APIs and retention terms**
- Anthropic (page dated 1 Jul 2026): API inputs/outputs deleted from the backend within 30 days, except longer-retention services you control (e.g. Files API), zero-data-retention agreements, Usage Policy enforcement or legal requirements; flagged content kept up to 2 years and classifier scores up to 7 years; "for Covered Models, we require limited data retention and review as part of our safety work" (no effective date on that page) — [Anthropic Privacy Center](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-commercial-api-data)
- OpenAI: abuse-monitoring logs retained up to 30 days by default; Zero Data Retention excludes content from logs for eligible endpoints — [OpenAI developer docs](https://developers.openai.com/api/docs/guides/your-data); OpenAI's obligations under the NYT preservation order (which had required indefinite retention of consumer and non-ZDR API content) ended 26 Sep 2025 — [OpenAI](https://openai.com/index/response-to-nyt-data-demands/) (secondary summary); OpenAI has previewed "Private Safety Processing" that would require 30-day retention on its most capable models (preview) — [The Next Web](https://thenextweb.com/news/openai-zero-data-retention-private-safety-processing) (secondary)
- Google Gemini API: unpaid services (incl. free API quota/AI Studio) content may be used to improve Google products and may be read by human reviewers (after disconnection from account/key); paid services content is not used for product improvement but is logged for a limited period for policy-violation detection; enabling Cloud Billing makes all usage "Paid"; in EEA/Switzerland/UK paid-service terms apply to all usage — [Gemini API terms (Oct 2025 archive)](https://ai.google.dev/gemini-api/terms-archive/terms_10_07_25); [Sep 2025 archive](https://ai.google.dev/gemini-api/terms-archive/terms_09_25_25) (secondary summary)
- In-tenant routing: claude-code-action supports Bedrock, Google Cloud Agent Platform (Vertex) and Microsoft Foundry via OIDC with no static cloud credentials — [Claude docs](https://code.claude.com/docs/en/github-actions); PR-Agent supports Azure OpenAI, Bedrock, Vertex AI, OpenRouter, Ollama via LiteLLM; when self-hosted with your own key, data handling is between you and the LLM provider — [qodo-ai/pr-agent](https://github.com/qodo-ai/pr-agent)
- Hosted review services concentrate risk: CodeRabbit's compromise exposed a GitHub App key with access to ~1M repos incl. private ones; Qodo Merge Pro's RCE could have exposed customer code — [Kudelski CodeRabbit](https://kudelskisecurity.com/research/how-we-exploited-coderabbit-from-a-simple-pr-to-rce-and-write-access-on-1m-repositories); [Kudelski Qodo](https://kudelskisecurity.com/research/qodo-dynaconf-aws-admin-key-leaked-twice)
- Leaked AI-tool credentials have downstream data value: Check Point notes Anthropic Workspaces let multiple keys share access to cloud-stored project files, so a stolen API key can expose workspace data — [The Hacker News](https://thehackernews.com/2026/02/claude-code-flaws-allow-remote-code.html) (secondary)

**Self-hosted models and the quality trade-off**
- PR-Agent docs: local open-source models (Ollama/vLLM) "are suitable for experimentation and learning purposes (mainly for the `ask` command)" but "not suitable for production-level code analysis tasks"; "for production workflows and real-world usage, we recommend using commercial models"; Ollama's default context window "may be too small for PR-Agent prompts and pull-request diffs" (example uses `qwen2.5-coder:32b` with 64K context) — [PR-Agent docs](https://docs.pr-agent.ai/usage-guide/changing_a_model/)
- Kodus markets self-hosting with BYO LLM so code and LLM calls stay inside the network **[VENDOR STATEMENT]** — [Kodus](https://kodus.io/self-hosted-ai-code-review/)

**Licences**
- PR-Agent: launched under Apache 2.0 (2023), later changed to AGPL v3; Qodo announced on 23 Apr 2026 that it donated PR-Agent to the community org `The-PR-Agent` and is moving back to Apache 2.0 — [Qodo blog](https://www.qodo.ai/blog/qodo-is-handing-pr-agent-over-to-the-community/); however, as fetched in Nov 2026 both `The-PR-Agent/pr-agent` and `qodo-ai/pr-agent` display an **MIT** licence (conflict with the Apache 2.0 announcement) — [The-PR-Agent/pr-agent](https://github.com/The-PR-Agent/pr-agent); [qodo-ai/pr-agent](https://github.com/qodo-ai/pr-agent)
- Kodus: "AGPL core"; self-hosted free under AGPLv3 **[VENDOR STATEMENT, LICENSE file not checked]** — [Kodus repo/search summary](https://github.com/kodustech/kodus-ai)
- run-gemini-cli: Apache-2.0 — [README](https://github.com/google-github-actions/run-gemini-cli); claude-code-security-review: MIT — [repo](https://github.com/anthropics/claude-code-security-review)

**Cost runaway and abuse**
- Anthropic: each run consumes GitHub Actions minutes plus API tokens; recommends specific prompts, concise CLAUDE.md, `--max-turns`, workflow-level timeouts and concurrency controls — [Claude docs](https://code.claude.com/docs/en/github-actions)
- Open triggers are a cost vector: codex-action warns `allow-users: "*"` "can lead to API key abuse", e.g. off-topic requests consuming quota — [codex-action security.md](https://github.com/openai/codex-action/blob/main/docs/security.md)
- Retries multiply calls: PR-Agent retries rejected requests on the same model up to `config.num_retries` (default 4) before falling back; simple `/review` or `/ask` may be one call but "retries, fallbacks, and larger reviews may need more" — [PR-Agent docs](https://docs.pr-agent.ai/usage-guide/changing_a_model/); [qodo-ai/pr-agent](https://github.com/qodo-ai/pr-agent)
- Trigger frequency is the biggest cost lever (every-push triggers multiply reviews) — [Codacy blog](https://blog.codacy.com/ai-code-review-cost-per-pull-request-what-engineering-teams-actually-pay-in-2026) **[VENDOR BLOG, secondary]**
- Stolen LLM keys (PromptPwnd, Comment and Control, Flatt) translate directly into third-party spend on the victim's account — [Aikido](https://aikido.dev/blog/promptpwnd-github-actions-ai-agents); [SecurityWeek](https://www.securityweek.com/claude-code-gemini-cli-github-copilot-agents-vulnerable-to-prompt-injection-via-comments/)

**Reliability of CI runs**
- Security fixes change behaviour: after GHSA-wpqr-6v78-jr5g, workflows relying on auto-trust fail to load workspace settings and workflows relying on old allowlist behaviour "may fail silently" — [OSV](https://osv.dev/vulnerability/GHSA-wpqr-6v78-jr5g)
- Platform changes break workflows: `pull_request_target` brownouts (9 and 16 Nov 2026) created failed runs; default block from 2 Dec 2026 — [GitHub changelog](https://github.blog/changelog/2026-11-02-pull_request_target-blocked-by-default-december-2); `actions/checkout` v7 fails pwn-request checkouts — [GitHub changelog](https://github.blog/changelog/2026-06-18-safer-pull_request_target-defaults-for-github-actions-checkout)
- Fork PRs get no secrets, so AI review silently does not run on external contributions in the standard setup; scheduled workflows in public repos are disabled after 60 days without activity; per Anthropic's docs, review workflows created "before v2.1.229" wrote the review only to the workflow run log (not to the PR) unless updated with `--comment` — [Claude docs](https://code.claude.com/docs/en/github-actions)
- run-gemini-cli warns that setting `DEBUG` makes the CLI hang waiting for a debugger — [README](https://github.com/google-github-actions/run-gemini-cli)
- Local models: mis-set context (`custom_model_max_tokens` vs `OLLAMA_CONTEXT_LENGTH`) causes "unexpected model output" — [PR-Agent docs](https://docs.pr-agent.ai/usage-guide/changing_a_model/)
- Unpinned harness versions (e.g. run-gemini-cli default `latest`) mean upstream changes land in CI without review — [README](https://github.com/google-github-actions/run-gemini-cli)

### Inferences
- For organisations with strict confidentiality, the realistic options are (a) hosted frontier models under ZDR or in-tenant routing (Bedrock/Vertex/Azure/Foundry) or (b) self-hosted open models accepting a quality drop; PR-Agent's maintainers themselves steer production users to commercial models.
- AGPL matters mainly if an organisation modifies the tool and offers it to others over a network (e.g. an internal platform used by external parties); PR-Agent's licence history (Apache → AGPL → announced Apache, displayed MIT) means the licence of the exact version/fork in use must be checked. (Inference; not legal advice.)
- Cost controls belong in the workflow (narrow triggers, actor gating, `--max-turns`, timeouts, concurrency) and at the provider (spend limits, separate restricted keys per repo), because a leaked or abused key is billed to the owner.

### Gaps
- No primary, well-documented incident of a runaway AI *code-review* bill was found (only practitioner blog anecdotes).
- No quantitative benchmark comparing local vs. commercial models on code-review quality was found beyond PR-Agent's qualitative guidance.
- Effective date of Anthropic's "Covered Models" retention requirement not confirmed (a secondary summary mentioned 9 Jun 2026).
- Gemini API paid-tier log retention period (exact days) not confirmed in current terms.
- Provider-specific rate-limit behaviour in CI (429/overload handling) was not researched in depth.
