The spine it fills in, so you can tell a run that went sideways from one that did not:

  1. `loam status` — where this feature actually is, and what is owed before you start
  2. `loam context` — the briefing: the service's living slice, and every delta in flight over it
  3. `loam delta` — the task: the intent, every requirement (outlined, then read one at a time), the endpoints, and the calls in and out
  4. `loam tasks` — the open units, ordered; `--next` is the single next unit, with the scenario verbatim and the fact that closes it
  5. `loam gherkin` in the service's repo — the digest-stamped `.feature` files. Never edit them
  6. write step definitions for the generated scenarios first, outside the generated directory
  7. implement until the suite passes, running it with a JSON report
  8. honour the contract in both directions: expose every inbound operation, call every outbound one
  9. `loam rebase` if building made you change the feature's documents at all, then validate the feature

Every step above is a `loam` invocation, and each command's own `--json` output
carries what to do next: findings have stable codes, and `loam status --json` puts
the ordered `next[]` — each entry a code and the literal command — in one place.
Branch on the codes, never on the prose. The check workflow prints without its fix
tables; use `loam explain <code>` for each code the run actually reports, and pass
`--fix-tables` only when you deliberately need the complete table.
